# 花大夫拍照识别与档案匹配设计

## 目标

用户进入花大夫后直接提交一张新照片，系统先识别植物品类并尝试匹配花园里的已有植物。识别不应成为问诊门槛：匹配不到时仍以“新朋友”身份完成问诊，问诊结束后再由用户选择是否建立档案。

## MVP 匹配策略

一期采用“视觉品类识别 + 本地档案匹配”，不宣称能够识别同品类中的具体植株。视觉模型返回标准品类、展示名称和置信度；前端使用标准品类与用户花园数据匹配。没有真实参考照片库之前，不做不可靠的个体级视觉比对。

- 恰好一个同品类档案：自动认作该老朋友并进入问诊。
- 多个同品类档案：展示紧凑候选列表，请用户确认是哪一盆，也允许选择“都不是”。
- 没有同品类档案或识别置信度不足：以新朋友身份直接进入问诊。
- 识别请求失败：不阻断问诊，以“暂未识别的新朋友”继续，并显示可重试的轻提示。

## 用户流程

`拍照 → 识别动效 → 自动匹配老朋友 / 必要时确认候选 / 新朋友 → 真实问诊 → 生成病历 → 新朋友可选择建档`

识别成功但不需要用户判断时不增加中间确认页，只在问诊页顶部显示“认出是罗罗（绿萝）”或“正在看一位新朋友（多肉）”。多候选确认页沿用首页卡片的渐变头图与植物剪影，不使用圆形头像。

## 接口与数据

阿里云函数增加 `recognize` 动作，输入为压缩后的照片及用户花园中的轻量候选资料，候选只包含 `id`、`name`、`species`，不上传日记正文。返回结构为：

```json
{
  "ok": true,
  "recognition": {
    "species": "绿萝",
    "confidence": 0.87,
    "matchedIds": ["plant-id"],
    "note": "叶片形态与绿萝相符"
  }
}
```

后端只允许返回输入候选中真实存在的 ID；前端仍会二次校验 ID，避免模型生成不存在的档案。识别结果只用于路由，不作为医学诊断结论。

## 问诊与建档

老朋友的诊断病历继续保存到原档案。新朋友完成问诊后进入现有建档流程，自动带入识别出的品类和本次病历；用户可以命名、补充性格，也可以跳过建档。跳过时不在花园中留下半成品植物。

## 验证标准

自动化测试覆盖单候选自动匹配、多候选确认、无候选新朋友、识别失败降级、非法候选 ID 丢弃，以及识别后仍能完成真实问诊。人工验证需检查 390×844 页面、请求期间状态、无横向溢出、控制台无错误，并确认 API Key 始终只存在于阿里云函数环境变量中。
