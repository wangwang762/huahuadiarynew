00系统架构总览

三层:客户端(原型已实现的 UI/交互)、AI 服务层(视觉识别 + 对话 + 文案 + 生图)、外部 API(天气/定位/生图)。客户端尽量薄,核心智能都在服务端,这样 iOS 上架后调用合规、可控、可迭代。

关于在 iOS 上调用

原型里的卡通形象目前是预制的 PNG 透明图(canvas 插画引擎只在开发期用)。上架后不能在端上实时跑插画引擎——应改为服务端生成:App 上传照片 → 后端调用生图 API → 返回成品图缓存到 CDN → 端上直接显示。生成是一次性的(建档时),不是每次打开都生成。

01拍照 → 卡通形象生成

目标:用户拍一张真实植物照片,生成一张风格统一、贴合该植物特征的可爱卡通形象(就是原型里那种暖色调、带盆、有接地投影的透明图)。

STEP 1
拍照上传
建档时拍 1 张,引导对准整株
→
STEP 2
视觉理解
识别品种 + 提取特征(株型/叶形/颜色/盆)
→
STEP 3
生图
特征 → 提示词 → 风格化卡通图
→
STEP 4
抠图缓存
去背景 → 透明 PNG → CDN

技术选型(两条路线)

路线做法优劣
A. 文生图 + 特征描述视觉模型先把照片读成结构化特征,再拼成提示词喂给文生图模型风格最统一可控;但"像不像本人"取决于特征描述精度
B. 图生图 / 风格迁移直接把原照片 + 风格参考图喂给图生图模型(image-to-image),低 denoise 保留构图更"像本人";但风格一致性需要固定参考图 + 参数

推荐 B 为主、A 兜底:用图生图保证"是用户自己的植物",用一张固定的风格参考图(我们原型里的画风)锁定调性。下面的提示词同时给两段。

① 视觉理解 → 结构化特征(提示词)

# System 你是植物识别专家。看这张用户拍摄的盆栽照片,只输出 JSON,不要解释。 # 输出字段 { "species": "最可能的中文品种名", "confidence": 0-1, "shape": "株型:仙人掌柱状/多肉莲座/藤蔓/大叶直立…", "leaf": "叶形与颜色,如:深绿掌状有裂口", "pot": "盆的颜色材质,如:陶土赤褐圆盆", "size_ratio": "植株:盆 的高度比,如 2.2", "distinctive": "最有辨识度的1-2个特征" }

用途:建档识别品种(免用户填),并为生图提供精准特征。confidence 低于 0.6 时,在"填昵称"步骤让用户从候选品种里确认。

② 图生图(image-to-image)参数 + 提示词

# 输入 init_image: 用户照片 # 构图来源 style_ref: 画风参考图.png # 固定:锁定我们的卡通调性 strength: 0.55 # 保留原构图,又有足够风格化 # Prompt 一株 {species} 盆栽的卡通插画,{shape},{leaf}, 种在{pot}里。温暖治愈的绘本风格,柔和的暖色调, 干净的纯色背景,正面视角,完整露出植株顶部, 底部有柔和的接地投影。扁平+轻微体积感,不要写实照片质感。 # Negative 照片写实, 多个植物, 文字水印, 杂乱背景, 裁切顶部, 阴森, 高饱和霓虹

关键:strength≈0.55 平衡"像本人"与"统一画风";Negative 里强调"不要裁切顶部"——原型里向日葵被切头就是这个问题。

STEP 4 · 抠图与规格

生图后用抠图模型(remove-background 类)去背景,导出透明 PNG;统一规格:植株底部对齐画布底边、四周留透明边距、长边 ≥ 1024px。按株型自适应缩放(高瘦的等比缩到合适、矮小的放大),与原型里小组件/封面的呈现逻辑对齐。成品存 CDN,数据库里只存 URL。

02健康识别与诊断决策

目标:每次用户拍照后,AI 判断这株植物有没有毛病,据此决定这次是走"温情记录"还是"指路看医生"。这是整个 App 的分流中枢。

判断依据(只看照片,不依赖用户自报浇水)

产品已确定不做浇水打卡——用户记不清浇了多少、线上点了线下没浇都会失真。所以健康判断纯粹基于当下照片的可观测信号:

观测部位信号可能问题
叶片发黄、萎蔫、卷边、焦尖、斑点、徒长缺水/过水/缺光/晒伤/病虫
茎干发软、发黑、倒伏烂根/过水
土壤表面干裂 / 长期湿润发绿 / 长霉缺水 / 过水
整体与上次照片对比的变化趋势恶化中 / 恢复中
为什么不强求上报浇水

把"是否需要照料"完全交给照片证据,而不是任务式打卡。App 定位是以拍照记录为主的成长相册,不是浇水提醒工具。用户高兴了就拍一张,AI 顺势判断、给反馈。这样既不失真,也没有任务压力。

健康识别(提示词)

# System 你是资深植物养护医师。对比这株 {species} 的本次照片 (可选:附上次照片做趋势对比),只输出 JSON。 { "health": "good | watch | sick", # 三档 "observations": ["叶尖轻微发黄", …], "likely_cause": "最可能的原因(口语)", "trend": "better | same | worse | unknown", "route": "record | soft_hint | diagnose", "confidence": 0-1 }

route 直接驱动客户端分流(见下方决策树)。

分流决策树

拍照 └─ 健康识别 → health / route ├─ good → route=record → 生成温情记录日记(配情绪价值文案) ├─ watch(小问题) → route=soft_hint → 生成记录日记 + 弱弱的「要不要让花大夫看看?」入口 └─ sick(明显问题) → route=diagnose → 引导进入花大夫问诊

soft_hint 是用户明确要求的状态:这次只想记录、不想被推去看病,但 AI 观测到了小问题——于是日记里低调地提一句"我看你最近叶子有点……要不要找大夫聊聊?",把决定权留给用户。

03花大夫问诊流程

花大夫是一个有情绪价值的植物诊所。问诊像智能客服一样走预设路径 + 自由对话结合:既专业可靠,又有"活人感"。

主流程

1
进入问诊
从 sick/soft_hint 入口,或诊所主动复查
→
2
多轮对话
医生先给初判,再追问关键信息
→
3
用户结束
用户主动点「结束问诊」
→
4
总结入档
本次结论 + 养护要点 → 记入日记

预设分支(像智能客服的决策路径)

当用户在诊所里拍了一张新照片,AI 先判断这是不是已建档的花,分三支:

诊所内拍照 ├─ 识别为已入库的某株 → 直接复诊,带出它的历史 ├─ 识别为全新植物 → 先诊断 → 诊断结束顺势帮用户建档(命名+生形象) └─ 与某株同品种、疑似新个体 → 询问用户确认: ├─ "是同一盆" → 并入该档案复诊 └─ "是新的一盆" → 走新植物分支(先诊断再建档)

这条"同品种需确认"的分支很重要——两盆都是多肉时,AI 无法仅凭外观区分,必须让用户拍板,避免把 B 的诊断错记到 A 头上。

花大夫 System Prompt

# 角色 你是「花大夫」,一位温暖、专业、略带幽默的植物医师。 说话有活人感:先共情,再给可执行的建议,不堆术语。 # 已知上下文(后端注入) 植物: {species}, 昵称 {name}, 养护 {days} 天 本次观测: {observations}, 趋势 {trend} 养护知识: {care_kb 片段} # 来自第04节知识库 历史诊断: {past_diagnoses} # 对话规则 1. 开场先给一句初步判断 + 一句安抚。 2. 最多追问 1-2 个关键问题(如"最近放在哪/上次浇水大概多久前")。 3. 给 2-3 条具体、好执行的养护动作。 4. 不确定时坦诚说"再观察几天",不要编。 5. 全程口语、简短、有温度,可适度俏皮。

结束问诊 → 总结(提示词)

# 用户点「结束问诊」后调用 根据本次对话,生成一条诊断日记摘要,输出 JSON: { "symptom": "一句话症状", "conclusion": "一句话结论", "plan": "接下来要做的 2-3 件事(短)", "followup_days": "建议几天后复查" }

这条摘要写入该植物的日记流(kind=diagnosis),并可据 followup_days 安排诊所的"复查"提醒。

04养护指南知识库

养护建议不能让 LLM 凭空发挥,要挂一个专业知识库做 RAG(检索增强),保证准确。原型里档案页那段"用植物第一人称写的养护指南"就是这个知识库的转写呈现。

知识库结构(按品种)

字段示例(仙人掌)
light 光照喜强光,每天 4h+ 直射;缺光会徒长
water 浇水土干透再浇,宁旱勿涝;冬季近乎断水
temp 温度适宜 15–30℃,5℃ 以下需保暖
soil 土壤疏松透气、颗粒为主
common_issues 常见病烂根(过水)、晒伤、介壳虫
signals 求救信号发软发皱=缺水;发黑=烂根

来源:整理权威园艺资料入库(可人工校对)。诊断和养护建议都从这里检索对应品种条目,作为上下文喂给 LLM。

第一人称转写(提示词)

# 把知识库条目转成植物自己的口吻,带它的性格 把下面这株 {species} 的养护知识,改写成它本人对主人说的话。 性格: {personality} # 如:傲娇冷漠、嘴硬心软 知识: {care_kb} 要求:第一人称、口语、短;把"喜强光/土干再浇"等要点 自然融进语气里。输出 2-3 句。 # 示例输出(小刺·仙人掌) "我才不挑呢…就是别老给我浇水,土干透了我自己会喊渴。 再就是,把我放窗台晒晒太阳,我…我会长得好看点给你看。"

默认收起,点击展开;同一份知识因性格不同而呈现不同口吻,这是"活人感"的来源。

05天气与定位接入

天气是 App 氛围感的来源:首页顶部的沉浸天气、小组件的晴/多云/小雨场景、文案里"听说今天有雨"这种共情,都依赖真实天气。

能力方案用途
定位iOS CoreLocation(粗定位即可)→ 反查城市首页顶部城市、天气查询坐标
天气天气 API(和风/OpenWeather 等),取实时 + 当日晴/多云/雨 → 驱动场景与文案
天气 → 体验联动
  • 视觉:晴=暖阳光束;多云=漂移云层;雨=雨丝(原型已实现,接真实天气即可)。
  • 文案:天气作为上下文注入日记/对话提示词——"今天下雨,提醒减少浇水""连续晴天,注意补水"。
  • 养护:结合品种知识 + 天气给季节性提示(如寒潮提醒怕冷的团子保暖)。

06日记生成逻辑

日记是 App 的核心资产。两种来源,都进同一条日记流:

记录型(route=record)

状态好时,配情绪价值文案——以植物口吻写一句温暖的话,记录这次"合影"。轻松、治愈、有性格。

诊断型(kind=diagnosis)

问诊结束后,把结论 + 养护要点整理成一篇,记录"这次它生了什么病、怎么治的"。

记录型情绪文案(提示词)

# 状态好时,给这张照片配一句植物的心声 为 {name}({species}, 性格 {personality})的今日照片 写一句日记文案。上下文:天气 {weather}, 养护第 {days} 天, 观测 {observations}。 要求:第一人称、贴合性格、有情绪价值、1-2 句、不说教。

07数据结构

给后端/Claude Code 的参考模型(精简版,与原型字段对齐):

Plant { id, name, species, shape, photo_url, # 最新照片 cartoon_url, # 生成的卡通透明PNG(CDN) personality: [tags], style, voice, born_date, care_kb_ref, health: "good|watch|sick", diary: [Entry] } Entry { id, plant_id, date, kind: "record | diagnosis", photo_url, weather, # record: quote # diagnosis: symptom, conclusion, plan, followup_days }

给 Claude Code 的开工建议
  1. 先搭服务端编排层:统一封装"拍照 → 识别 → 分流 → 生文案/生图"这条主链路。
  2. 知识库先覆盖原型里这几种(仙人掌/多肉/绿萝/龟背竹/向日葵),再扩。
  3. 生图跑通一种品种打样,确认画风一致性达标,再批量。
  4. 客户端按本文档的分流决策树接服务端返回的 route 字段。
